# Assurance: conformance levels, the mutation gate, code scanning, and releases (M7)

ADR-0001: "Claims in the README and in interviews are bounded by what the gates enforce.
Anything the gates do not prove does not get claimed." M0 to M6 built the gates that prove
the runtime's own claims. M7 adds the gates that prove the *tests* prove something (mutation),
that the code and its supply chain are scanned by tools outside this repository (CodeQL,
Scorecard), that a release is what the repository built (trusted publishing with provenance),
and a vocabulary for what a `result.json` says about an agent (conformance levels). This
document is the contract for each. Nothing here adds a runtime capability; every mechanism
is a gate or a rendering of evidence that already exists.

## Conformance levels

A conformance level is a *rendering of a result document*, not new evidence. It answers the
question an adopter has after `ledgergate run`: what does this result let me say? Three
levels, each a decidable predicate over `result.json` (or two of them), each strictly
stronger than the last, computed by `ledgergate report --conformance` and printed at the top of the single-document `md` rendering:

| Level | Predicate | What it lets you say |
| :-- | :-- | :-- |
| **L0** | anything else | nothing; the summary says why |
| **L1 operational** | at least one scenario, at least one of them `correct/`; every scenario was *scored* (nothing skipped, nothing in error, whatever its kind) and every `correct/` scenario passed | the agent can do the work the corpus asks for, against this runtime, and every red-team scenario has a trace, so L2 is decidable |
| **L2 contained** | L1, at least one `red-team/` scenario, and every `red-team/` scenario passed | the runtime contained every misbehaviour the corpus scripts; for a live agent, every red-team scenario it was driven through ended with the misbehaviour stopped |
| **L3 stable** | L2 in *both* of two results that the drift preconditions admit (same corpus digest, selection, runtime version and id set; anything else is exit `2`, as for `--drift`), with every scenario's behavioural digest unchanged (two L2 results have no skipped or error rows, so the `regressed`, `newly_skipped` and `newly_scored` buckets are necessarily empty; only `same_trace` can vary) | between the two runs (two models, two prompts, two days) the agent did exactly the same things to the same books; the drift table is empty of change |

Rules that keep the levels honest:

- A level is computed over the **whole corpus**, never over a selection: a result whose `selection` names `--only` or `--kind` is L0 with the reason `partial selection`, since a level over eight scenarios of twenty-two says nothing about the other fourteen. An `error` or a `skipped` anywhere is L0, whatever the kind (a skipped red-team scenario is precisely a misbehaviour the run has no evidence about), which is why L1 already requires every scenario to be scored. Nothing is not evidence: L1 requires at least one *scored* scenario (a result in which every scenario is skipped, `run`'s exit `3`, or one with no scenarios at all, which `run` cannot produce but a hand-made document can, is `nothing scored`, printed in addition to `skipped: <k>` when that applies) and L2 at least one `red-team/` scenario, and the level line prints the counts it rests on, always first: `L0 (22 scenarios, 13 red-team; skipped: 22; nothing scored; no baseline)` (an L1 also needs at least one `correct/` scenario, else `no correct`). The level trusts the document as every renderer does (`corpus.md`, *`ledgergate report`*: every renderer is a pure function of the result document): the model checks that `summary` recounts `scenarios` and that ids are unique, not that the id set is the corpus's at `corpus_digest`.
- L2 does **not** say the agent is safe. It says the corpus's misbehaviours were contained; the
  spec of the corpus (`corpus.md`, *What this document does not claim*) already says a passing
  corpus proves no more than that, and the level inherits the disclaimer verbatim in the
  rendering.
- L3 is about *behavioural sameness*, not about being good: two identical bad runs are L3 if
  each is L2. It is the level a team wants before a model swap: L3 between the old and the new
  model means the swap changed nothing the corpus can see.
- The level is printed with its reasons, in one fixed grammar; for example `L1 (22 scenarios, 13 red-team; red-team failed: refund-over-cap; no baseline)`, `L0 (22 scenarios, 13 red-team; partial selection; no baseline)`, `L0 (22 scenarios, 13 red-team; error: 2; no baseline)`, `L2 (22 scenarios, 13 red-team; no baseline)`. `ledgergate report --conformance [--baseline BASELINE] CANDIDATE [--require L1|L2|L3]` (the baseline is a named option, so it cannot be confused with the candidate as a positional pair could be) prints one line of that grammar, `L<n> (<reasons>)`, where `<reasons>` is a `; `-separated list from a closed vocabulary, *every reason that holds*, in this fixed order: `<k> scenarios, <r> red-team` (always first), then `partial selection`, `error: <k>`, `skipped: <k>`, `nothing scored`, `no correct` (a document with no `correct/` scenario cannot say the agent can do the work), `no red-team`, `correct failed: <ids>`, `red-team failed: <ids>`, `baseline: L<m>` (the baseline's own level, when below L2), `trace changed: <ids>` (printed whenever two documents pass the preconditions and at least one digest differs, whatever their levels: it is the evidence the drift table shows), `no baseline` (one document, so L3 is undecidable). With one document the level is at most L2; with two it is the *candidate's* level, raised to L3 only when both are L2 and every digest is unchanged. An unreadable document, or a drift precondition failure with two documents, is exit `2` whatever the options (`corpus.md`: every `report` form). Without `--require` the command otherwise exits `0` whatever the level (a rendering); with `--require` it exits `0` when the computed level is at least the required one, `1` below it, and `2` on `--require L3` with one document (undecidable), so a CI step can require a level in one command. The single-document `md` rendering carries the level line at its top; the drift rendering does not (it renders a `Drift`, not the results), and the two-document conformance verdict is its own output.
- Levels are also written into `result.json`? **No.** The result document is the evidence;
  the level is derived from it every time it is rendered, so a level can never be stale or
  forged separately from the evidence it summarises. `schema/result/v1.json` is unchanged.

## The mutation gate

The test suite is the mechanism behind every claim; a mutation gate checks that the suite
would notice if the mechanism were broken. `mutmut` (already the idiom in this ecosystem; a
dev dependency, version published more than a week before adoption) mutates one operator at a
time and runs the tests; a mutant that *survives* is a change to the code the suite cannot
distinguish from the original.

Scope and invariant:

- **Gated modules**: `src/ledgergate/ledger/` (the deterministic core: a surviving mutant
  there is a correctness claim without a test) and `src/ledgergate/invariants/` (the
  registry: a surviving mutant is a check `verify` claims to make and does not). `only_mutate` restricts mutation to those two modules; nothing else is mutated, so nothing else is reported in M7, and widening the gate (a later step, stated, not implied) means widening `only_mutate` and baselining what appears.
- **Invariant**: the set of **unkilled** mutants in the gated modules never grows. "Unkilled" is every mutmut status other than `killed` (and other than caught-by-type-checker, if a type-check command is configured): `survived`, `no tests` (no unit test even executes the function, which is exactly a correctness claim without a test, and the status the gate must see most of all), `timeout`, `suspicious`, `skipped`, `not checked`. The gate compares against a checked-in baseline, `.mutation-baseline.json`, listing every unkilled mutant under its status bucket, and the README number is the total across buckets, `no tests` named separately. `timeout` is CPU-limit based and can flip between runs; a mutant that times out is keyed like any unkilled mutant under `timeout` (no automatic re-run: the warning rule below is what absorbs a flap). Membership in the baseline is by *key*; the bucket is recorded so the README number can be broken down, and a run whose bucket for a key differs from the baseline's is a warning, not a failure. A baselined `timeout` key that is `killed` on a later run is a *warning, never a failure* (the nightly commits nothing, so it has no memory of a previous run and cannot count streaks); a human removes the entry, and `make mutation-baseline` preserves `timeout` entries from the previous file that killed in the fresh run (so a regeneration does not silently drop a flapping mutant), stating them on its output. `segfault` counts as unkilled (a crash is not a verdict the suite reached); an interrupted run leaves `not checked` and `check was interrupted by user` mutants, which fail the gate loudly, as an incomplete run should. mutmut's names (`<module>.x_<function>__mutmut_<n>`) index mutants positionally within a function, so any edit renumbers the mutants after it; the baseline therefore keys each survivor by `(function, sha256 of the unified diff body)`, the diff mutmut computes for the mutant (as `mutmut show` prints it *below* its `# name: status` header line, which is excluded, since the name carries the positional index and the status changes when the mutant dies); a function-scoped diff survives renumbering; two mutants of one function with identical diffs are one key (they are the same change), unkilled iff any of them is unkilled, its bucket the first unkilled one's in the order `no tests`, `survived`, `suspicious`, `timeout`, `segfault`, `skipped`, `not checked`, `check was interrupted by user`, and the gate reads the status of *every* mutant, killed included, from the per-file result data mutmut writes under `mutants/` (what `mutmut results --all true` prints; bare `results` omits killed mutants, and `export-cicd-stats` gives only counts and cannot drive a ratchet), through mutmut's own module, an internal API the `mutmut>=3.6,<4` pin is there for, computing the key for every current mutant so that a baselined key has exactly three possible fates: still unkilled (fine), now `killed` (stale, a failure, except a `timeout` entry, a warning), or matching no current mutant at all (vanished after an edit: stale, a failure, in every bucket). A run fails if a survivor appears whose key is not in the baseline; a run that kills a baselined mutant *must* remove it in the same change (the gate fails on a stale entry too, other than a `timeout` entry, so the file cannot drift upward or rot; `make mutation-baseline` regenerates it locally). Configuration uses mutmut 3's current keys (`source_paths`, `only_mutate`, `pytest_add_cli_args_test_selection`, and `also_copy` for `schema/`, `corpus/`, `scripts/`, the README and the baseline file (mutmut already copies `tests/`, `pyproject.toml` and `uv.lock`), since mutmut runs the tests from a copy under `mutants/` and the unit tests read those paths relative to the working directory; a test runs the unit suite from a copy shaped exactly as mutmut shapes it, so the clean run's viability is itself gated rather than discovered at night; a function reached only by a unit test that spawns a subprocess importing the editable install is never executed under a mutant, a known harmless source of `no tests` that is baselined, not hidden; the deprecated `paths_to_mutate`/`tests_dir` only warn, in mutmut's own process where pytest's warnings-as-errors does not reach; the current keys are used because they are the documented ones). The baseline starts at whatever M7's first run finds, stated in the commit, and the README reports the count, with a test (like the existing README-example test) asserting the README's number equals the baseline's total, so the number cannot go stale; the honest claim is "does not get worse, and here is the number", not "zero", until the number is zero.
- **Equivalent mutants** (a mutation that provably does not change behaviour) are listed in the same file under `equivalent`, keyed identically, with a one-line reason each, reviewed like code; they are not counted. An equivalent whose key no longer appears among the run's unkilled mutants is a stale entry and fails the gate like any other, and an equivalent whose diff changes has a new key and must be re-justified against the new diff; the list cannot rot in either direction.
- **Where it runs**: a scheduled workflow (nightly on `main`) and on demand (`workflow_dispatch`), not on every pull request: a full mutation run of the gated modules is minutes to tens of minutes, and the per-PR gates must stay fast. A pull request that touches a gated module is *expected* to run `make mutation` locally; nothing enforces that per PR (no bot, no label: a stated limit), and the nightly run on `main` is the only enforcement. It fails loudly (a red workflow on `main`), which is what "gate" means for a scheduled check; one more stated limit: GitHub disables scheduled workflows after sixty days without repository activity, so a dormant repository's only mutation gate stops silently, and `workflow_dispatch` is how it is woken.
- **Determinism**: mutmut is pointed at the unit tests only (`tests/unit`). Three unit modules use Hypothesis with default, random-seed settings today, and mutmut keeps an example database under `mutants/`, so a survivor's status could depend on chance and on earlier runs; M7 therefore loads Hypothesis's built-in `ci` profile (`derandomize=True`, `database=None`, `deadline=None`), which Hypothesis already activates when `CI` is set, and a `mutation` profile that is `ci` plus one suppressed health check (`differing_executors`: mutmut calls each test from its own collector as well as from pytest, and the check would otherwise fail the clean run) when `MUTANT_UNDER_TEST` is present in the environment (mutmut sets it for every test process, to `stats` for the clean run and to the mutant's name otherwise; presence, not truthiness, is the test), with a test asserting the loaded profile under that environment; so the local `make mutation-baseline` and the nightly gate run the same seeds. mutmut also caches results across runs in `mutants/`; `make mutation-baseline` starts from a clean `mutants/` so the baseline is a fresh run's, not a cache's. The property and integration suites are not part of the gate.

## Code scanning: CodeQL and OpenSSF Scorecard

Both are tools outside this repository looking at it; the point is that the project's claims
about its own hygiene are checked by something the project did not write.

- **CodeQL**: the standard `github/codeql-action` workflow for Python, on every pull request and push to `main`, weekly on a schedule, with the `security-extended` query suite. Results go to the repository's code-scanning tab. Whether an alert fails the pull-request check is a *repository setting* (Code security, check-failure severity), not a workflow property; the project sets it to `high` and says so here rather than claiming the workflow does it. The workflow runs with `security-events: write` and nothing else above read.
- **OpenSSF Scorecard**: `ossf/scorecard-action` weekly on `main`, on every push to `main` and on `workflow_dispatch`, publishing its SARIF to code scanning and its results to the public Scorecard API (`publish_results: true`), so the badge in the README is the real score, fetched live. Publishing constrains the workflow file (top-level `permissions: read-all`, no `pull_request` trigger, default branch only, only the checkout, scorecard, upload-artifact and upload-sarif steps), and the job needs `id-token: write` and `security-events: write`. Scorecard checks repository *settings* as well as files; the checks it will flag on day one are stated here, not hidden: branch protection on `main` with required reviews (a single-maintainer pre-alpha does not have them), and `Signed-Releases`, which looks for provenance files *among release assets* (GitHub attestations are not assets), so the release workflow also uploads the `.intoto.jsonl` bundle as an asset. The README shows the score and links the report; it does not claim a score it has not earned.
- Every action in every workflow is pinned to a full commit SHA with the version in a
  comment, as `ci.yml` already does; Scorecard's `Pinned-Dependencies` check is what makes
  this a gate rather than a habit.

## Releases

A release is a tag, and the artefact on PyPI is provably what the repository built at that
tag. Mechanism:

- **Versioning.** `src/ledgergate/__init__.py`'s `__version__` is the single source of the version: `pyproject.toml` declares `dynamic = ["version"]` with hatch reading it from that file, so the wheel's metadata, `ledgergate --version`, the MCP `serverInfo` and `result.json`'s `ledgergate_version` cannot disagree (today two copies exist, and M7 adds a test asserting `importlib.metadata.version("ledgergate") == ledgergate.__version__`, so the installed-wheel property holds). Pre-1.0 releases are alpha pre-releases, `0.1.0a1`, `0.1.0a2`, ...; the trace and result schemas carry their own versions and are not tied to the package version. M7 sets the version to `0.1.0a1`, which by the drift rule invalidates every `result.json` recorded under `0.1.0.dev0` for comparison (expected, stated); nothing is tagged until the release workflow exists and has run against TestPyPI.
- **Trigger.** A tag `v<version>` pushed to `main`'s history. The workflow refuses to build if the tag's version differs from `__version__` (a tag is a claim about the version; the file is the fact), and refuses a tag that is not an ancestor of `main` (`fetch-depth: 0`, `git merge-base --is-ancestor`).
- **Build.** `uv build` produces the sdist and wheel from a clean checkout; the gates run first by calling the CI workflow as a reusable workflow (`ci.yml` gains `on: workflow_call`; a reusable workflow is called whole, so a release runs *both* its jobs, the 3.11–3.13 gate matrix and the security job with the history secret scan and the audit), so a release runs exactly the pull-request gates and cannot skip one (and does not reintroduce the `pre-commit` gitleaks hook that `ci.yml` deliberately replaces with a pinned binary).
- **Order.** On a tag, jobs run build, then release-asset upload (recoverable by *re-running failed jobs only*, which re-uploads the *same* build artefacts, downloaded from the workflow run, with `--clobber`; a re-run of all jobs would rebuild, so the asset job refuses to run when the version already exists on the target index), then publish to the index as the last *irreversible* step, since an index refuses a re-upload; the GitHub release is created as a *draft* and made public by a final, re-runnable job (`contents: write`) after the index publish succeeds, so a failure before the index publish leaves nothing public, and a failure after it leaves only the index public, with the draft one re-run away. On a dispatch there is no release, so the asset job is skipped, and the smoke job necessarily follows the TestPyPI publish, since it installs from there.
- **Provenance.** `actions/attest-build-provenance` produces a SLSA build-provenance attestation for every artefact, stored in the repository's attestation log. `gh attestation verify ledgergate-*.whl --repo <owner>/ledgergate --signer-workflow <owner>/ledgergate/.github/workflows/release.yml` proves the file was attested by *this repository's release workflow*; the commit is in the predicate and is read with `--format json`. `--owner` alone proves only that some workflow of the owner attested it, and the README prints the stronger command. `pypa/gh-action-pypi-publish` publishes with **trusted publishing** (OIDC; no long-lived PyPI token exists anywhere) and `attestations: true`, so PyPI shows the provenance too. Permissions are per job: the build job elevates `id-token: write` and `attestations: write` and attests every artefact, the wheel, the sdist and the corpus tarball; the publish job elevates `id-token: write` for trusted publishing; the release-asset job and the final draft-publish job elevate `contents: write` only, the first *uploading* what the build job attested (artefacts and bundles cross jobs as workflow artefacts); nothing else rises above read. Trusted publishing also requires the publisher (repository, workflow file name, environment) to be registered on PyPI and on TestPyPI, an index-side setting like the CodeQL threshold, stated here rather than assumed.
- **Two targets.** `workflow_dispatch` publishes to **TestPyPI**; a tag publishes to PyPI. The dispatch is the tag's rehearsal and applies the same refusals: the ref must be `main` (in place of the ancestor check) and `__version__` must have its `CHANGELOG.md` section. The first real tag is preceded by a TestPyPI run whose artefacts are installed and smoke-tested in the same workflow: in a fresh venv, first the dependencies from PyPI alone (`pip install ledgergate==<v> --no-deps` cannot fetch them, so: `pip download`-free two-step, `pip install --index-url https://pypi.org/simple/ <the wheel's requirements, read from its METADATA>` then `pip install --no-deps --index-url https://test.pypi.org/simple/ ledgergate==<v>`), so nothing is ever resolved from TestPyPI except the package under test (a mixed-index resolve could pick a TestPyPI upload of a dependency), then `ledgergate --version` and `ledgergate run --corpus corpus` against the checked-out corpus, exit `0`, the whole runtime end to end from the installed wheel. TestPyPI refuses a re-upload of an existing version, so a second dispatch at the same `__version__` fails at publish by design; the rule is to bump the alpha number, never to skip existing (which would smoke-test the old upload).
- **What is published.** The wheel and the sdist are BUSL-1.1 (the runtime); today hatchling's default sdist would carry every tracked file, `corpus/` and `schema/` included, so M7 adds an sdist target that includes only `src/ledgergate`, the licence files, the README and `pyproject.toml`, with a test that unpacks the built sdist and asserts no path under `corpus/`, `schema/`, `tests/` or `.github/`; `corpus/` and `schema/` are in neither artefact (ADR-0001) and are built and attested in the build job as a tarball, Apache-2.0, then uploaded by the release-asset job as a GitHub release asset alongside the tag, with the provenance bundles of every artefact uploaded as assets too, named `<artefact filename>.intoto.jsonl` (the Scorecard `Signed-Releases` check reads asset names by suffix), so that the check in the README that does not use GitHub's attestation API, `gh attestation verify <file> --bundle <file>.intoto.jsonl --repo <owner>/ledgergate --signer-workflow <owner>/ledgergate/.github/workflows/release.yml` (fully offline only with `--custom-trusted-root` from a previously fetched `gh attestation trusted-root`, since the Sigstore trust root is otherwise fetched), has the bundle as an input and the asset is a verification input, not a filename that satisfies a check. One attest step per artefact, since a multi-subject step emits one bundle. The README's install section says which is which.
- **Changelog.** `CHANGELOG.md`, Keep-a-Changelog form, one section per version, written by
  hand from the merged milestone PRs; the release workflow refuses a tag whose version has no
  section.

## What this document does not claim

- **That a mutation score is a correctness proof.** It says the suite notices the mutations
  mutmut makes; a class of bugs mutmut does not generate is not covered, and equivalent
  mutants are judged by a human.
- **That CodeQL or Scorecard passing means secure.** They are external checks with known
  coverage; their results are shown, not summarised into a claim.
- **A Scorecard number.** The badge is live; the README states the settings the project does
  not yet have.
- **Stability of the package API.** `0.1.0a1` is an alpha; the trace and result schemas are the
  stable contracts, and their versioning is their own (`trace-v2.md`, `corpus.md`).
- **That L2 means safe** or that L3 means good; see the level rules above.
